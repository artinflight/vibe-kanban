---
title: Codex home isolation
description: Diagnose and repair Vibe Kanban instances that accidentally run Codex from a shared home directory.
---

Vibe Kanban should run Codex with its own `CODEX_HOME` when the same machine also runs interactive Codex sessions. If VK falls back to `~/.codex`, VK agents can share authentication state, rollout history, and session metadata with tmux or terminal Codex sessions.

This can make agent sessions look confusing after restarts or service updates. Raw logs may include full previous thread history, repeated-looking turns, or unexpected fork/resume state from the shared Codex home.

<Warning>
Do not restart `vibe-kanban.service` while agents are running unless you are willing to interrupt those runs. Check for active execution processes first.
</Warning>

## Expected local configuration

For the local MCP-managed VK instance, the expected Codex home is:

```bash
/home/mcp/.local/share/vibe-kanban/codex-home
```

The user service should include this drop-in:

```ini
[Service]
Environment=CODEX_HOME=/home/mcp/.local/share/vibe-kanban/codex-home
```

A checked-in copy lives at:

```text
docs/self-hosting/systemd/codex-home.conf
```

## Fast diagnosis

Use this when agents appear to repeat themselves, resume the wrong context, or produce unexplained `thread/fork` behaviour after a VK service change.

<Steps>
<Step title="Check for active agents">
  Query the live database before restarting VK:

  ```bash
  python3 - <<'PY'
  import sqlite3

  con = sqlite3.connect(
      'file:/home/mcp/.local/share/vibe-kanban/db.v2.sqlite?mode=ro',
      uri=True,
  )
  con.row_factory = sqlite3.Row

  rows = con.execute("""
  SELECT lower(hex(ep.id)) process_id, ep.started_at, ep.status, w.name, w.branch
  FROM execution_processes ep
  JOIN sessions s ON s.id = ep.session_id
  JOIN workspaces w ON w.id = s.workspace_id
  WHERE ep.status = 'running'
  ORDER BY ep.started_at DESC
  """).fetchall()

  print('running_count', len(rows))
  for row in rows:
      print(dict(row))
  PY
  ```

  <Check>
  It is safe to restart only when `running_count` is `0`, or when you explicitly accept interrupting the listed runs.
  </Check>
</Step>

<Step title="Inspect the service environment">
  Check the configured and live environments:

  ```bash
  systemctl --user cat vibe-kanban.service
  systemctl --user show vibe-kanban.service -p Environment -p MainPID

  pid="$(systemctl --user show -p MainPID --value vibe-kanban.service)"
  tr '\0' '\n' < "/proc/$pid/environ" | rg '^CODEX_HOME='
  ```

  The live process should report:

  ```bash
  CODEX_HOME=/home/mcp/.local/share/vibe-kanban/codex-home
  ```
</Step>

<Step title="Inspect a Codex app-server log">
  Open a recent process JSONL file under:

  ```text
  /home/mcp/.local/share/vibe-kanban/sessions
  ```

  Search for `codexHome`:

  ```bash
  rg -n '"codexHome"' /home/mcp/.local/share/vibe-kanban/sessions
  ```

  A healthy VK-launched Codex process should report:

  ```json
  {"codexHome":"/home/mcp/.local/share/vibe-kanban/codex-home"}
  ```

  If it reports `"/home/mcp/.codex"`, VK is sharing the interactive Codex home.
</Step>
</Steps>

## Stale rollout path audit

Run this before a backend restart and after any Codex-home migration, blue/green
cutover, or backup restore. A thread row can point at a retired `CODEX_HOME`
even when the current service environment is correct. If that rollout file is
missing, resume/fork can fail with errors like:

```text
thread/resume request failed: failed to resolve rollout path ...
thread/fork request failed: no rollout found for thread id ...
```

That is a recovery problem. Do not treat it as fixed by starting a fresh Codex
thread unless the operator explicitly accepts losing the old thread context.

<Warning>
When there are blue/green or retired VK instances, audit every relevant Codex
home, not just the currently active service environment.

Example on the MCP host:

- current green may use `/home/mcp/.local/share/vibe-kanban-green-codex-home`
- retired blue may have used `/home/mcp/.local/share/vibe-kanban/codex-home`

If `state_5.sqlite` points at a rollout in the retired home, restore that exact
file from the matching Desktop archive. Do not rewrite the thread to a new
rollout path or start a new thread unless the operator accepts context loss.
</Warning>

<Steps>
<Step title="Check recently active Codex threads">
  Query the live Codex state database and verify rollout files exist:

  ```bash
  python3 - <<'PY'
  import os
  import sqlite3

  db = '/home/mcp/.local/share/vibe-kanban/codex-home/state_5.sqlite'
  con = sqlite3.connect(db)
  con.row_factory = sqlite3.Row

  rows = con.execute("""
  SELECT id, rollout_path, cwd, title, datetime(updated_at, 'unixepoch') updated
  FROM threads
  WHERE updated_at >= strftime('%s', 'now', '-1 day')
  ORDER BY updated_at DESC
  """).fetchall()

  missing = [row for row in rows if not os.path.exists(row['rollout_path'])]
  print('recent_threads', len(rows))
  print('missing_recent_rollouts', len(missing))
  for row in missing:
      print(dict(row))
  PY
  ```

  <Check>
  Do not declare resume state safe while `missing_recent_rollouts` is non-zero.
  Restore the files from backup or report the exact unresolved thread ids.
  </Check>
</Step>

<Step title="Check active execution rollouts">
  For every running execution, map the VK turn to the Codex agent session id and
  verify that thread's rollout exists:

  ```bash
  python3 - <<'PY'
  import os
  import sqlite3
  import uuid

  vk_db = '/home/mcp/.local/share/vibe-kanban/db.v2.sqlite'
  codex_db = '/home/mcp/.local/share/vibe-kanban/codex-home/state_5.sqlite'

  vk = sqlite3.connect(vk_db)
  vk.row_factory = sqlite3.Row
  codex = sqlite3.connect(codex_db)
  codex.row_factory = sqlite3.Row

  rows = vk.execute("""
  SELECT ep.id, ep.status, ep.started_at, w.name, w.branch,
         cat.agent_session_id
  FROM execution_processes ep
  JOIN sessions s ON s.id = ep.session_id
  JOIN workspaces w ON w.id = s.workspace_id
  LEFT JOIN coding_agent_turns cat ON cat.execution_process_id = ep.id
  WHERE ep.status = 'running'
  ORDER BY ep.started_at DESC
  """).fetchall()

  print('running_count', len(rows))
  for row in rows:
      process_id = str(uuid.UUID(bytes=row['id']))
      agent_session_id = row['agent_session_id']
      rollout_path = None
      exists = None
      if agent_session_id:
          thread = codex.execute(
              'SELECT rollout_path FROM threads WHERE id = ?',
              (agent_session_id,),
          ).fetchone()
          if thread:
              rollout_path = thread['rollout_path']
              exists = os.path.exists(rollout_path)
      print({
          'process_id': process_id,
          'workspace': row['name'],
          'branch': row['branch'],
          'agent_session_id': agent_session_id,
          'rollout_path': rollout_path,
          'rollout_exists': exists,
      })
  PY
  ```
</Step>

<Step title="Restore missing stale rollout files">
  If a missing path points at a retired Codex home, search same-day and older
  Desktop session backups. Restore only the missing rollout JSONL to the exact
  path recorded in `state_5.sqlite`; do not rewrite the database unless the
  referenced file is unrecoverable and the operator approves a fallback.

  Record:

  - the missing thread id
  - the path recorded in `state_5.sqlite`
  - the backup archive that contained the rollout
  - the restored file path and size
  - the post-restore audit showing the rollout exists
</Step>
</Steps>

## Saved-message preference trap

Saved messages are stored in `UI_PREFERENCES`, but the DB row is not the whole
truth. The running backend can deserialize the JSON into a typed structure and
serialize it back without fields that exist in SQLite. In that failure mode:

- SQLite still contains `saved_chat_messages`
- `/api/scratch/UI_PREFERENCES/...` omits `saved_chat_messages`
- `/api/scratch/UI_PREFERENCES/.../stream/ws` omits `saved_chat_messages`
- desktop and mobile show no saved messages

For preference recovery, verify all three layers:

```bash
sqlite3 "$VK_DB" "select payload from scratch where scratch_type='UI_PREFERENCES';"
curl -fsS "$VK_URL/api/scratch/UI_PREFERENCES/00000000-0000-0000-0000-000000000001"
```

Then verify the WebSocket initial patch or use a browser smoke. Do not claim
saved messages are fixed from a SQLite-only check.

## Repair the live service

Only run these commands after active VK agents finish, or after you decide it is acceptable to interrupt them.

<Steps>
<Step title="Install the drop-in">
  Copy or recreate the drop-in:

  ```bash
  mkdir -p ~/.config/systemd/user/vibe-kanban.service.d
  cp docs/self-hosting/systemd/codex-home.conf \
    ~/.config/systemd/user/vibe-kanban.service.d/codex-home.conf
  ```
</Step>

<Step title="Reload and restart VK">
  Apply the new environment:

  ```bash
  systemctl --user daemon-reload
  systemctl --user restart vibe-kanban.service
  ```
</Step>

<Step title="Verify the repair">
  Confirm the process environment and health endpoint:

  ```bash
  systemctl --user is-active vibe-kanban.service

  pid="$(systemctl --user show -p MainPID --value vibe-kanban.service)"
  tr '\0' '\n' < "/proc/$pid/environ" | rg '^CODEX_HOME='

  curl -fsS http://127.0.0.1:4311/api/info >/dev/null
  ```

  <Check>
  New VK-launched Codex sessions should now report the isolated Codex home in their raw app-server logs.
  </Check>
</Step>
</Steps>

## Interpreting repeated-looking output

Not all repetition has the same cause.

- Full-thread payloads in raw JSONL logs can contain old turns. This is expected in `ThreadStartResponse`, `ThreadForkResponse`, and `thread/started` data.
- Rebase or merge conflicts can make agents describe the same conflict several times if Git replays multiple commits that touch the same files.
- A real isolation failure is present when VK-launched Codex app-server logs report `codexHome: /home/mcp/.codex`.

If the isolated home is correct and the UI still displays duplicated transcript entries, investigate the log normalisation and chat rendering paths next.

## Do not copy only auth.json

When creating or restoring the isolated Codex home, carry forward the Codex session and rollout state as well as authentication files. Existing workspace thread fork/resume can depend on those files.

Copying only `auth.json` can cause old workspace threads to fail with:

```text
thread/fork request failed: no rollout found for thread id ...
```
